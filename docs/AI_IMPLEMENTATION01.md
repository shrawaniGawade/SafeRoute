## 1. Purpose

This document explains how the AI/ML part of SafeRoute will be built in **3 days (Days 5–7)**: which data is used, what the model predicts, how it is trained and evaluated, and how it connects to the app.

**Main principle:** build a **small, real, and honestly evaluated** model. It must not be the weighted score relabelled as AI.

---

## 2. Where AI Fits in SafeRoute

SafeRoute uses **two separate scoring methods**:

| | Rule-based Safety Score | ML risk estimate |
|---|---|---|
| **What** | Weighted sum of 6 factors | Predicted probability that an area is high-incident |
| **How** | A fixed formula with configurable weights | Learned from historical labelled data |
| **Strength** | Transparent and always available | Learns patterns from the data that fixed weights miss |
| **Role** | Main score, used for the recommendation | Supporting, independent estimate shown next to it |
| **If unavailable** | — | The app falls back to the rule-based score only |

**Why keep both:** the rule-based score can be explained and works everywhere. The ML estimate shows genuine machine learning. If the two disagree, that is useful information for the user.

```
Route geometry ──> Sample points ──┬──> Safety Engine (rules) ──> Safety Score 0–100
                                   │
                                   └──> ML Service (/predict-route) ──> Risk probability
                                                                         (+ model version)
                                         ▼
                              Route card: "Score 82 · AI risk: Low (0.18)"
```

## 3. Current State and Gap

| Item | Current (`ai/`) | Problem | Target |
|---|---|---|---|
| Training data | Random synthetic numbers | Not real data | A documented public incident dataset |
| Target `y` | Generated by a fixed formula | The model only re-learns the formula, so it is not real ML | A label taken from real incident counts |
| Model | `RandomForestRegressor` | No baseline, no classification metrics | Baseline + Logistic Regression + Random Forest classifier |
| Evaluation | MAE on a random split | Random split can leak data | Time-based split; precision, recall, F1, ROC-AUC |
| Metadata | None | Version and metrics cannot be shown | `model_meta.json` |
| API | `POST /predict` (4 manual features) | Not connected to real route locations | `POST /predict-route` (points + time) |
| Node client | `aiService.ts` with a formula fallback | Fallback is not clearly labelled | Fallback flag shown as a UI badge |

The current demo stays available as the **labelled fallback**, so nothing breaks while the real model is built.

## 4. Problem Definition

**Explanation:** a model is only meaningful if what it predicts is clearly defined. A vague target such as "how safe a road is" cannot be labelled or evaluated.

| Item | Definition |
|---|---|
| **Unit of prediction** | One **grid cell** (about 250 m × 250 m) during one **time band** (Night 22–06, Morning 06–12, Afternoon 12–18, Evening 18–22) |
| **Target (`y`)** | `high_incident = 1` if the cell and time band's incident count in the **label period** is in the top 25% of non-zero cells; otherwise `0` |
| **Task** | Binary classification |
| **Output** | `P(high_incident)` from 0 to 1, mapped to Low (< 0.33), Moderate (0.33–0.66), or High (> 0.66) |
| **Route-level result** | Mean and maximum probability across the cells the route passes through |

**Avoiding leakage:** features use only the **history period** (for example months 1–9), and labels use only the later **label period** (months 10–12). The model therefore predicts the future from the past and never sees the answer.

## 5. Dataset Selection

**Explanation:** the dataset is the biggest risk. It must be **chosen on Day 1** of the project, not on Day 5.

### 5.1 Selection Criteria
- Each incident has **latitude and longitude** (point-level, not district totals)
- Each incident has a **date and time**
- At least 12 months and at least 10,000 records for one city
- An open licence that allows use in a project
- Clear documentation of the fields

### 5.2 Candidate Datasets

| Dataset | Type | Granularity | Notes |
|---|---|---|---|
| Chicago Crimes (Chicago Data Portal) | Crime | Point + timestamp | Large, well documented, open |
| UK police.uk street-level crime | Crime | Anonymized point + month | No time of day; use with accident data |
| UK STATS19 road accidents | Accidents | Point + timestamp | Good for the accident factor |
| NYC Motor Vehicle Collisions | Accidents | Point + timestamp | Large, open |
| India NCRB / data.gov.in | Crime | District / state per year | **Too coarse** for route-level ML; use only for context |

**Recommendation:** use the **same city** for both the demo map and the dataset (for example Chicago: crimes + OSM lighting + OSM facilities). If the demo must use an Indian city, keep the ML model trained on the documented city and **label it clearly** in the UI. Otherwise, present the ML component as an extension.

### 5.3 Supporting Features from OpenStreetMap
- `lit=yes/no` on roads → lighting ratio for each cell
- Points of interest (shops, transit stops) → activity proxy
- Hospitals, police stations, and fire stations → distance to nearest facility

## 7. Day 5 – Dataset and Feature Engineering

**Goal:** a clean, reproducible training dataset.
**Explanation:** most ML problems come from the data, not the algorithm. Getting this day right makes Day 6 straightforward.

| # | Step | Brief details |
|---|---|---|
| 5.1 | Download and document | Save to `data/raw/`; write the source, licence, date range, and row count in `data/README.md` |
| 5.2 | Clean | Drop rows with missing or invalid coordinates, duplicates, and points outside the city's bounding box; parse timestamps |
| 5.3 | Assign cells | Round coordinates to a grid (about 250 m) or use H3 resolution 9 → `cell_id` |
| 5.4 | Assign time band | Hour → Night, Morning, Afternoon, or Evening |
| 5.5 | Split the period | History period (features) and label period (target), split by **time** |
| 5.6 | Build features | See the table below |
| 5.7 | Build labels | Count of incidents in the label period → top 25% = 1 |
| 5.8 | Train/val/test split | Split **by cell groups**, so neighbouring cells don't leak: 70 / 15 / 15 |
| 5.9 | Save | `train.csv`, `val.csv`, `test.csv`, plus `cell_features.csv` for use at inference |

### Feature Set

| Feature | Source | Why it helps |
|---|---|---|
| `hist_incidents_band` | History-period count, same cell and band | Past incidents predict future ones |
| `hist_incidents_total` | History-period count, all bands | Overall activity level of the cell |
| `neighbour_incidents` | Sum over the 8 surrounding cells | Spatial context |
| `night_ratio` | Night incidents ÷ total | Shows whether risk is concentrated at night |
| `time_band` | One-hot (4 bands) | Risk varies by time of day |
| `is_weekend_share` | Share of incidents at weekends | Temporal pattern |
| `lit_ratio` | OSM `lit` tags in the cell | Lighting proxy |
| `poi_density` | OSM POI count | Activity proxy |
| `dist_emergency_m` | Distance to the nearest facility | Access to help |

**Output:** a validated, reproducible dataset. Running `python model/prepare_data.py` regenerates it.

## 8. Day 6 – Model Training and Evaluation

**Goal:** a trained model with documented, honest results.
**Explanation:** a model only counts as useful if it **beats a simple baseline** on data it has never seen.

### 8.1 Models

| Model | Why |
|---|---|
| **Baseline 1:** majority class | The minimum any model must beat |
| **Baseline 2:** "high if `hist_incidents_band` is in the top 25%" | A strong rule based on common sense; the model must add something beyond it |
| **Logistic Regression** | Simple and interpretable (its coefficients can be explained) |
| **Random Forest Classifier** | Captures non-linear patterns; provides feature importance |

### 8.2 Steps

| # | Step | Brief details |
|---|---|---|
| 6.1 | Pipeline | `StandardScaler` + model in a single sklearn `Pipeline`, saved as one object |
| 6.2 | Class imbalance | `class_weight="balanced"`; also check the PR-AUC |
| 6.3 | Tune on validation | Small grid search: LR `C`; RF `n_estimators`, `max_depth`, `min_samples_leaf` |
| 6.4 | Choose the threshold | Pick the threshold that maximizes F1 on the validation set (not the default 0.5) |
| 6.5 | Final test | Evaluate **once** on the test set; record the metrics |
| 6.6 | Leakage check | Train vs. test gap; check that no label-period data is in the features |
| 6.7 | Select | Prefer the simpler model (LR) unless RF is clearly better (more than 0.02 ROC-AUC) |
| 6.8 | Save | `safety_model.joblib` + `model_meta.json` |

### 8.3 Metrics

| Metric | What it tells you |
|---|---|
| **Precision** | Of the cells predicted high-risk, how many really were |
| **Recall** | Of the truly high-risk cells, how many were caught |
| **F1** | Balance of precision and recall |
| **ROC-AUC** | How well the model ranks risky cells above safe ones (0.5 = random) |
| **PR-AUC** | Ranking quality when the high-risk class is rare |
| **Confusion matrix** | Counts of each type of error |

## 9. Day 7 – Prediction API and Integration

**Goal:** a working AI prediction flow from start to finish in SafeRoute.
**Explanation:** the backend sends route points and the time. The ML service looks up each cell's features, predicts, and returns a combined result for the route. The backend never has to know which features the model uses.

### 9.1 FastAPI Endpoints

| Method | Endpoint | Purpose |
|---|---|---|
| GET | `/health` | `{status, model_loaded, version}` |
| GET | `/model-info` | Returns `model_meta.json` (for the admin dashboard and the "How is this calculated?" popover) |
| POST | `/predict-route` | **Main endpoint:** route points + time → route risk |
| POST | `/predict` | Existing demo endpoint, kept for backward compatibility |

### 9.2 `/predict-route` Contract

**Request**
```json
{
  "points": [{ "lat": 41.8781, "lng": -87.6298 }, { "lat": 41.8790, "lng": -87.6310 }],
  "departure_hour": 22,
  "weekday": 5
}
```

**Response**
```json
{
  "risk_probability_mean": 0.21,
  "risk_probability_max": 0.58,
  "risk_level": "Low",
  "coverage": 0.86,
  "cells_evaluated": 14,
  "model": "RandomForestClassifier",
  "model_version": "1.0.0",
  "data_type": "real_public",
  "warning": "Estimate based on historical reported incidents only. Not a safety guarantee."
}
```

`coverage` is the share of points whose cell exists in the training area. If it is below 0.6, `risk_level` is set to `"Insufficient data"`.

### 9.3 Steps

| # | Step | Brief details |
|---|---|---|
| 7.1 | Load once | Load the model, metadata, and `cell_features.csv` at startup into memory |
| 7.2 | Validate input | Pydantic: lat −90–90, lng −180–180, hour 0–23, up to 500 points |
| 7.3 | Map to cells | Point → `cell_id` → feature row; unknown cells count against coverage |
| 7.4 | Predict | `predict_proba` for each cell → mean and max → risk band |
| 7.5 | Node client | Extend `backend/src/services/aiService.ts` with `predictRouteRisk(points, hour)`, a 3-second timeout, and the URL from `AI_SERVICE_URL` |
| 7.6 | Fallback | On failure, return `{aiEstimate: null, fallback: true}`. Don't mix in the formula silently |
| 7.7 | Route analysis | Add `aiEstimate` to each route in the `/api/routes/search` response |
| 7.8 | UI | Route card chip "AI risk: Low (0.21)", the model version, coverage, and the warning; badge "AI estimate unavailable" on fallback |
| 7.9 | Admin | Show ML status, version, test metrics, and average latency in the admin dashboard |

**Output:** a search in the app shows the AI estimate. Stopping the ML service shows the fallback badge, and the app keeps working.

## 13. Limitations and Responsible Use

- **Reporting bias:** crime data records **reported** incidents only. Areas that are policed more heavily may look riskier than they are.
- **Stigma risk:** the app must not label neighbourhoods as "dangerous". It shows route-level estimates with context.
- **Coverage:** the model only applies inside the area it was trained on. Elsewhere it shows "Insufficient data".
- **Staleness:** patterns change over time, so the training period is shown and retraining is planned.
- **Not a guarantee:** every AI output shows a warning that it does not guarantee safety.
- **Synthetic demo:** the current demo model is labelled `synthetic_demo` until the real model replaces it.

## 14. Interview Questions and Answers

| Question | Short answer |
|---|---|
| What does your model predict? | Whether a 250 m cell will be high-incident in a given time band, using only past data |
| How is that different from the Safety Score? | The score is a fixed weighted formula. The model learns from labelled historical data and is checked on a held-out test set |
| How did you avoid leakage? | Features come from an earlier period and labels from a later one; data is split by cell groups |
| Why Logistic Regression? | It is simple, interpretable, and a strong baseline. Random Forest was compared against it |
| How do you know the model is useful? | It beats both the majority-class and the history-rule baselines on F1 and ROC-AUC |
| Class imbalance? | Balanced class weights, a tuned threshold, and PR-AUC reported |
| What if the ML service is down? | The backend times out after 3 seconds; the rule-based score is shown with a fallback badge |
| Main limitation? | Reporting bias and coverage limited to the training city |
| How would you improve it? | More data sources, regular retraining, model calibration, user feedback labels |
